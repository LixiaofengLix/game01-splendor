## 0. 待你确认的默认决策

| 项 | 默认选择 | 理由 |

## 1. 架构总览

```
                ┌──────────── 表现层（可替换）────────────┐
                │ debug_ui/（最小验证界面） → 将来正式 UI  │
                └───────────────▲─────────────────────────┘
                                │ 信号（state_changed / events）
┌──────────────┐   Action   ┌───┴────────────┐   Action   ┌─────────────────────┐
│PlayerController├─────────▶│ GameController  │◀──────────┤ Human / Bot / LLM / │
│（座位控制器）  │           │（对局流程，Node）│           │ Remote（联网）       │
└──────────────┘           └───┬────────────┘           └─────────────────────┘
                               │ 调用
                ┌──────────────▼──────────────┐
                │ core/（纯逻辑，RefCounted，无 Node 依赖）│
                │ GameState · Action · Rules  │
                └──────────────▲──────────────┘
                               │ 读取
                        data/*.json（卡牌、贵族、规则参数、AI 权重、提示词）
```

核心原则：

1. **逻辑与表现分离**：`core/` 只有纯数据和纯函数，不依赖场景树。这样 AI 可以复制状态做推演，可以无界面批量模拟，联网时主机能直接拿来校验动作，正式 UI 也能直接替换掉调试界面。
2. **一切操作都是 Action**：拿宝石、预留、购买、弃宝石、选贵族都是同一种数据对象。人类、程序 AI、大模型、远程玩家都只是“产出 Action 的控制器”，对局流程不需要区分它们。
3. **状态可序列化**：`GameState.to_dict(viewer_seat)` / `from_dict()`，字典里带 `schema_version`，读取时校验版本。存档、联网同步、喂给大模型、加载测试场景都用这一套；`viewer_seat` 用来隐藏别人看不到的信息（牌堆顺序、他人盲抽预留的牌）。
4. **随机可复现**：使用带种子的 `RandomNumberGenerator`，同一个种子开局完全一致。存档同时保存“种子 + 动作序列”，可以完整重放，方便复现 bug。
5. **Action 只用稳定引用**：引用卡牌用 `card_id`，盲抽用等级，引用玩家用座位号，绝不使用“场面第几张”这类索引或坐标。
6. **只有规则引擎看完整状态**：AI、大模型、客户端和界面拿到的都是 `to_dict(viewer_seat)` 过滤后的视图。合法动作只依赖可见信息（牌堆只需要剩余张数），所以任何一方都能从自己的视图算出合法动作。
7. **数据驱动**：卡牌、贵族、规则参数（人数对应的宝石数、胜利分数、持币上限、预留上限等）、AI 权重、大模型提示词全部放在 `data/`。代码里只保留枚举（如宝石颜色、动作类型、对局阶段）。

### 目录结构（按功能组织，脚本和场景放在一起）

```
res://
├── CLAUDE.md            # 给 AI 会话的项目约定（Claude Code 每个会话自动读取）
├── autoload/            # 全局单例：DataRegistry（数据）、AppConfig（用户设置）、NetworkManager
├── core/                # 纯逻辑：枚举、数据模型、GameState、Action、Rules
├── game/                # GameController、PlayerController 及其子类（人类/远程）
├── ai/                  # 程序 AI
├── llm/                 # 大模型客户端与 LLM 控制器
├── net/                 # 大厅、同步
├── debug_ui/            # 最小可验证界面（将来被正式 UI 取代）
├── data/                # JSON 数据、提示词模板
├── tests/               # 规则自检脚本（无界面）+ scenarios/ 手工测试用的预设局面 JSON
└── docs/                # 计划、进度、测试用例、UI 对接文档
```

每个文件夹都有一份简短的 `README.md`（几行，说明用途和关键文件）。

## 2. 编码约定（阶段 1 写入 `CLAUDE.md`）

- 全部使用静态类型；核心类使用 `class_name`；文件名用 snake_case，类名用 PascalCase。
- 每个脚本开头用 `##` 文档注释写 1–3 行说明用途；只在不显而易见的地方写注释。
- `core/` 不引用 Node、场景和单例，规则参数通过 `RulesConfig` 对象传入。
- 不写魔法数字：规则数值都来自 `data/rules.json`。
- 信号用过去式命名（`state_changed`、`action_applied`）。
- 不做低价值的抽象：一个实现就不建接口，没有需求就不加配置项。
- AI、大模型、界面只能读 `to_dict(viewer_seat)` 视图，不能直接访问 GameState 内部字段（评审时用 grep 检查）。
- 文档只有一个来源：约定只写在 `CLAUDE.md`；文件夹 README 只写“这里放什么”；`PROGRESS.md` 只写状态和偏差。只建 `CLAUDE.md`（Claude Code 自动读取），不另建 `AGENTS.md`。
- 改动 `core/` 后必须跑一次规则自检（见阶段 2）。
- 每个阶段结束必须完成：代码 + 文件夹 README + 更新 `docs/PROGRESS.md` + 输出测试用例 `docs/tests/phase_N.md` + git 提交（等你验收后）。

## 3. 阶段划分

优先级：**规则正确 → 能玩 → 程序 AI → 大模型 AI → 联网 → 收尾**。
程序 AI 排在联网之前，因为联网测试可以用 AI 补座位，大模型 AI 失败时也需要程序 AI 兜底。

### 阶段 1：工程骨架与数据层

目标：能加载并校验全部游戏数据。

1. 初始化 git，在 `.gitignore` 里补上 `exports/`，写 `CLAUDE.md`（编码约定 + “新会话先读 PROGRESS.md”）、`docs/PROGRESS.md`。
2. 建好目录结构和每个文件夹的 README。
3. `core/enums.gd`：宝石颜色（白、蓝、绿、红、黑、金）、动作类型、对局阶段。
4. 数据文件：
   - `data/cards.json`：90 张发展卡（id、等级、颜色、分数、花费）。
   - `data/nobles.json`：10 位贵族（id、分数、要求）。
   - `data/rules.json`：各人数的宝石数（2 人 4 / 3 人 5 / 4 人 7）、金币 5、贵族数 = 人数 + 1、胜利分 15、持币上限 10、预留上限 3、“拿两枚同色”要求该色剩余 ≥ 4、每级翻开 4 张，以及若干规则细节开关（例如颜色不够时能否少拿）。
5. `core/card_data.gd`、`core/noble_data.gd`、`core/rules_config.gd`：类型化数据对象。
6. `autoload/data_registry.gd`：启动时加载 JSON 并校验，校验失败时报出具体条目。校验内容：
   - 每级 40/30/20 张；每级每种颜色 8/6/4 张；id 唯一；字段合法；单色花费不超过 7。
   - 锚点卡：例如三级 4 分红卡花费 7 绿。
7. 最小验证场景：打印数据统计，并把卡牌按“等级 + 颜色”排序输出成一页卡表，方便你对照实体卡人工核对。
8. 如果能找到可靠的开源卡表数据，就用它做一次交叉比对（一次性脚本，不进入正式代码）。

验收重点：数据数量和分布正确；故意改坏 JSON 时能看到明确的报错。
注意：卡牌数据由我按官方卡表录入，你需要用导出的卡表对照实体卡或官方卡表抽查。

### 阶段 2：核心规则引擎 + 文本调试台

目标：用文本命令完整打完一局，所有规则都正确。

1. `core/player_state.gd`：持有的宝石、已购卡牌（及其折扣）、预留卡牌、贵族、分数。
2. `core/game_state.gd`：银行宝石、三级牌堆、场面翻开的卡、贵族、当前玩家、回合数、阶段、终局标记、随机数状态；`to_dict(viewer_seat)` / `from_dict()` / `duplicate_state()`。
3. `core/action.gd`：动作数据 + 序列化 + 可读描述（日志和大模型都会用到），只用 `card_id`、等级、座位号做引用。
4. `core/rules.gd`（全部为静态函数）：
   - `setup(config, player_count, seed)`：按种子洗牌并发牌。
   - `get_legal_actions(view)`：只依赖可见信息。包括拿三枚不同色、拿两枚同色、预留场面卡、盲抽预留牌堆顶、购买（场面卡 / 自己预留的卡）、弃宝石、选贵族。
   - `apply(state, action) -> Array[GameEvent]`：内部先再校验一次合法性，然后执行动作并返回事件（供日志和 UI 使用）。
   - 支付规则：自动支付，先用折扣，再用同色宝石，最后用金币补差额（不让玩家手动选择用金币，避免复杂化）。
5. 规则细节清单（开关和数值放在 `rules.json`）：
   - 预留时附带 1 枚金币；金币用完时仍然可以预留，只是拿不到金币。
   - 每级场面固定 4 张；购买或预留后立即从同级牌堆补齐；牌堆空了，该位置就空着。
   - 牌堆空了就不能盲抽预留，只能预留场面卡。
   - 回合末流程：持币超过 10 → 进入弃宝石阶段 → 检查贵族（满足多位时进入选择阶段，每回合最多一位）→ 分数 ≥ 15 时触发终局，这一轮打完（所有人回合数相同）→ 结算（分数最高者胜；平分时购买卡牌少者胜；再相同则并列）。
   - 没有合法动作时自动跳过，跳过也算这名玩家的一个回合。
6. `debug_ui/console/`：文本调试台场景，支持命令 `new <人数> <种子>`、`state`、`legal`（列出带编号的合法动作）、`do <编号>`、`save <文件>` / `load <文件>`、`replay <文件>`。
7. `tests/scenarios/`：预设几个边界局面 JSON（快到 10 枚宝石、同时满足两位贵族、快要触发终局、某色宝石刚好剩 4 / 3 枚、牌堆已空等），用 `load` 直接进入。
8. 规则自检脚本 `tests/rules_selfcheck.gd`（无界面运行，例如 `godot --headless -s tests/rules_selfcheck.gd -- 2000`）：用随机合法动作跑 N 局，每一步检查以下不变量，一旦违反就输出种子和步数：
   - 宝石总数守恒；银行和玩家的宝石都不为负。
   - 回合结束时每人持币 ≤ 10；预留 ≤ 3。
   - 分数 = 卡牌分 + 贵族分。
   - 每局都能正常结束。
   - `to_dict` → `from_dict` 往返后状态一致。
   - 视图里不包含隐藏信息。

   这不是单元测试框架，只是一个脚本，后续阶段改动 `core/` 时跑一下即可。

验收重点：每条规则和边界局面；同一种子开局可复现；存档 / 读档 / 重放后状态一致；规则自检跑几千局无报错。

### 阶段 3：对局流程、座位控制器与最小可视化界面

目标：2–4 人同屏轮流用鼠标打完一局，并为 AI / 大模型 / 联网接入留好口子。

1. `game/player_controller.gd`：控制器基类，`request_action(view, legal_actions)`，决定后发出 `action_decided(action)` 信号。
2. `game/human_controller.gd`：从界面接收玩家点击。
3. `game/game_controller.gd`（Node）：持有 GameState，轮到谁就向谁的控制器要动作，校验后执行，并发出 `state_changed`、`events_emitted`、`game_finished` 信号。正式 UI 只需要监听这些信号。
4. `debug_ui/board/`：最小可视化桌面，全部用 Control + Button + Label，不做美术：
   - 银行宝石、三级场面卡、牌堆剩余数、贵族、各玩家面板（宝石 / 折扣 / 分数 / 预留卡）。
   - 只有合法的操作可以点（直接根据 legal_actions 启用或禁用）。
   - 弃宝石、选贵族的弹出选择框。
   - 事件日志面板。
5. `debug_ui/setup/`：开局设置界面，包括人数、种子、每个座位的类型（此阶段只有“人类”可用，其余选项先置灰）。
6. 存档 / 读档 / 重放、加载测试场景（复用阶段 2 的序列化）。
7. `docs/UI_INTEGRATION.md` 草稿（半页）：正式 UI 只依赖 GameController 的信号、`to_dict(viewer_seat)` 和 `Rules.get_legal_actions(view)`。调试界面严格按这份约定来写，阶段 7 再定稿。

验收重点：完整打完 2 / 3 / 4 人局；界面状态与规则一致；非法操作点不了。

### 阶段 4：程序 AI

目标：三档难度的电脑玩家，可以人机对战，也可以 AI 互打。

1. `ai/bot_controller.gd`：继承 PlayerController，有可配置的“思考延迟”，方便观察。AI 只接收过滤后的视图，看不到牌堆顺序和对手盲抽预留的牌；推演时，新翻开的牌视为未知（空位）。
2. `ai/evaluator.gd`：对局面和动作打分。考虑的因素：直接得分、离贵族的距离、折扣对目标卡的帮助、宝石利用效率、浪费的宝石、阻挡对手（预留对手最需要的卡）等。
3. 难度（权重和参数放在 `data/ai/easy.json`、`normal.json`、`hard.json`）：
   - 简单：贪心 + 随机扰动，偶尔犯错。
   - 普通：基于权重的一步评估 + 目标卡规划。
   - 困难：在普通基础上，用复制的视图推演“我方一步 + 对手回应”（两层搜索）。剪枝方法：先用一步评估给我方动作排序，只对前 K 个（K 约为 8–12，写在配置里）展开对手回应；超时就返回当前最优。
4. 无界面批量模拟：在阶段 2 自检脚本的基础上扩展，用 `godot --headless -- --sim 100 easy hard` 跑 N 局，输出胜率、平均回合数、平均分。为了抵消先手优势，每个种子跑两次并交换座位，同时报告样本量。这一步成本很低，但能快速判断难度梯度是否合理，调参也全靠它。
5. 开局设置界面启用“电脑（简单 / 普通 / 困难）”座位。

验收重点：AI 只做合法操作、不会卡死；难度梯度明显（用批量模拟的胜率衡量）；困难 AI 单步思考不超过约 1 秒。

### 阶段 5：大模型 AI

目标：任意座位都可以交给大模型，失败时自动由程序 AI 兜底。

1. `autoload/app_config.gd`：用户配置读写（`user://config.json`）。API Key 只存在 user 目录，不进仓库；提供示例文件 `data/llm/llm_config.example.json`。支持多个配置档（不同座位可以用不同模型对战）。
2. `llm/llm_client.gd`：基于 HTTPRequest 调用 OpenAI 兼容的 `/chat/completions`，处理超时、HTTP 错误，并记录 token 用量。
   - “构造请求 / 解析响应”集中在一个函数里，以后接 Anthropic 等非 OpenAI 格式的接口时只改这一处。不为此建抽象接口。
   - 优先尝试结构化输出参数（OpenAI 的 `response_format`、Ollama 的 `format`），服务不支持时退回文本解析 + 重试。
3. `llm/state_describer.gd`：把局面转成精简文本（用 `to_dict(viewer_seat)`），并把合法动作编号列出。调试模式下自动断言：发出去的文本里不包含牌堆里的 card_id，也不包含对手盲抽预留的 card_id。
4. 提示词模板 `data/llm/prompts/`：系统提示（规则摘要 + 输出格式，并明确“支付由系统自动完成，不需要指定用哪些宝石”）、回合提示（带占位符），以及可选的“性格”模板（激进、保守、阻挡型），全部数据驱动。
5. `llm/llm_controller.gd`：要求模型输出 `{"action": 编号, "reason": "..."}`；解析失败或编号非法时重试 N 次，仍失败则交给指定难度的程序 AI；模型给出的理由显示在日志里。每次调用有思考时间预算（可配置），超时就直接兜底；界面上显示已经等待的时间。
6. 调试界面增加大模型设置面板（base_url / key / model / 温度 / 超时）和“测试连接”按钮。

验收重点：能连接至少一家服务和一个本地 Ollama；断网、错误 Key、超时、模型乱回复时都能正确兜底；隐藏信息断言不触发。
预期：4 人局一局大约要调用 60–120 次大模型，整局较慢属于正常现象。

### 阶段 6：联网对战

目标：多台电脑通过局域网或 IP 直连对战，空座位可以由 AI 或大模型补上。

1. `autoload/network_manager.gd`：建主机 / 加入（ENetMultiplayerPeer）、连接 / 断开事件、协议版本校验（版本不一致时拒绝加入）。
2. `net/lobby/`：大厅界面与逻辑，包括昵称、座位分配、准备状态；主机可以把空座位设为 AI 或大模型；主机点击开始。
3. 主机权威同步：
   - 客户端通过 `rpc_id(1, submit_action, action_dict)` 提交动作。
   - 主机用 Rules 校验后执行，然后给每个客户端单独发送过滤后的状态 `to_dict(该玩家座位)` 和本次事件。状态数据很小，每次发全量，简单且不会出现不同步。
   - 主机不下发合法动作列表，客户端从自己的视图算出合法动作来启用按钮；主机仍然会重新校验。
   - `game/remote_controller.gd`：在主机上代表远程玩家，等待该玩家提交动作。
   - 客户端的 GameController 处于“镜像模式”，只负责显示，不推进规则。
   - AI 和大模型座位只在主机上运行。
4. 断线处理：掉线玩家的座位由程序 AI 接管。首次加入时，主机给客户端发一个随机 token（客户端保存在 `user://`），重连时凭 token 收回座位，不按昵称认主。
5. 公网说明（只写文档，不写代码）：IP 直连需要端口转发，推荐使用 Tailscale / ZeroTier 组成虚拟局域网。将来如果要做大厅或匹配服务器，只需要把 ENet 换成 WebSocketMultiplayerPeer，再加一个服务端。

验收重点：两三台电脑（或同一台电脑开多个实例）完整对局；混合人类、AI、大模型座位；客户端提交非法动作会被拒绝；掉线后 AI 接管并能重连。

### 阶段 7：整合收尾与 UI 对接

目标：功能闭环、可导出，并给正式 UI 开发留好接口文档。

1. 最小主菜单串起整个流程：本地游戏 / 联网游戏 / 设置 / 读档。
2. 设置持久化（昵称、AI 思考延迟、大模型配置档）。
3. 错误处理复查：数据加载失败、网络异常、大模型异常时给出明确提示。
4. `docs/UI_INTEGRATION.md`：正式 UI 需要监听的信号、可以调用的方法、状态字典的结构、事件类型列表。正式 UI 只需要替换 `debug_ui/`。
5. 导出预设（macOS / Windows），并在导出包上冒烟测试。
6. 清理：去掉临时数据和 TODO，补齐 README，更新 PROGRESS。

验收重点：导出包能完成本地对局、人机对局、大模型对局和联网对局。
需要你参与：Windows 包只能在 Windows 真机或虚拟机上验证；macOS 包如果要发给别人用，需要 Apple 开发者账号做签名和公证（只自己用可以跳过）。
